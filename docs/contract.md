# Aircraft load and balance contract

Flight-data preparers provide load stations with arm and station weight limit, positive loads assigned to stations, and an ordered gross-weight envelope whose forward/aft centre-of-gravity limits are linearly interpolated. Decimal strings use exact rational arithmetic. Total moment is the sum of weight×arm and centre of gravity is total moment/total weight.

A dispatch is allowed only when gross weight lies inside the envelope, centre of gravity lies between its interpolated limits, and every station remains within its own limit. The result preserves each station load and the distinct reason for an envelope failure. This repository does not calculate fuel burn, structural shear, take-off performance or certified aircraft limits.

The output is a structured planning data product, not an airline reservation system or operational flight release. Future fuel-tank sequencing can reuse station moments and envelope evidence.

## Trajectory scenarios

`process(data)` also accepts a trajectory scenario `{"stations": [...], "envelope": [...], "frames": [{"loads": [...]}, ...]}` with 2 to 20 frames. All frames of a scenario version share one station list and one envelope; each frame's load list follows the single-dispatch rules (1..1000 rows, load ids unique within the frame, decimal-string numbers). Load ids need not align across frames.

Between two adjacent frames every station's load varies linearly between its endpoint totals (a station without loads totals zero). Total weight, total moment and centre of gravity at any instant follow the same formulas as a static dispatch, and the forward/aft limits are piecewise-linear interpolations on the instantaneous gross weight. A version is eligible only when, at every instant of every closed inter-frame segment, gross weight stays inside the envelope weight range, centre of gravity stays within the interpolated limits (centre of gravity is judged only while the weight is inside that range), and every station stays within its limit. Touching a limit is not a violation. All checks use exact rational arithmetic: each comparison reduces to a quadratic inequality in the segment parameter whose closed-interval maximum is evaluated symbolically — never sampled, never tolerated, never extrapolated outside the envelope.

The result is `{"eligible": bool, "frames": [...], "violations": [...]}`. `frames` holds each frame's full single-dispatch result in input order. `violations` lists failing segments in ascending zero-based `segment_index` order, each with `envelope_reasons` (a subset of `weight_outside_envelope`, `forward_of_limit`, `aft_of_limit`, in that relative order, each at most once) and `over_limit_station_ids` (string-sorted). A violation exactly at a shared frame counts into every segment adjacent to that frame.

## TrajectoryDataset

`TrajectoryDataset(path)` persists scenarios and issuance receipts in a single file at `path`; closing and reopening the same path resumes the committed state. It is a library interface for one local process with a single writer — no command line, no external service.

- `put_scenario(scenario_id, revision, data)` commits the complete authoritative trajectory for `scenario_id` (a non-empty string) and returns its analysis. The first revision must be the integer `1`; each later revision must be exactly the current one plus one. Structurally invalid data or a wrong revision is rejected and changes nothing; a structurally valid but ineligible trajectory is still accepted as the current revision. Committing a new revision immediately revokes the scenario's outstanding receipts — they stay on file for audit but can no longer be consumed, even if the new version's numbers and eligibility are identical. Other scenarios are unaffected and old receipts are never migrated to the new revision.
- `issue(request_id, scenario_id, revision)` binds a dataset-unique non-empty `request_id` to the current, eligible revision and returns a receipt with `request_id`, `scenario_id`, `revision` and the issuance-time `analysis` — never the raw loads. Re-issuing with the same id and the same binding returns the original receipt unchanged, even if it can no longer be consumed; the same id with a different binding is rejected. Rejected requests do not reserve the id.
- `get_receipt(request_id)` returns the stored receipt unchanged. It is an audit query: it never re-analyses and never changes consumability.
- `consume(request_id)` is the simulated downstream claim: only while the receipt still names the current, eligible revision it returns `{"scenario_id", "revision", "data", "analysis"}` with the raw sample data, and it is repeatable. Unknown, stale or ineligible receipts return nothing.

Every mutation is one atomic file commit (write temp file, fsync, rename, fsync directory). If the process is interrupted during a single write, a reopen exposes either the state before or the complete state after the operation — never a partial one: a request id and its receipt, and a new current revision together with the revocation of older receipts, always take effect as a unit. A committed `issue` whose response never reached the caller is recognised on retry and never produces a second receipt. All invalid input, request conflicts and business rejections raise `ValueError`.
